## ADR-1（族同构）v6 行为向 v4 对齐，而不是反过来

**背景**：`PARENTCONTROL_QUOTA` 的 v4 链首有 2 条「放行家里」守卫（`-d <lan-v4-cidr> -j RETURN`、`-d 127.0.0.0/8 -j RETURN`，后者来自 `loopback` 静态节，**不是硬编码**）；v6 同链 0 条。封锁窗口内，受管设备能连家里（v4）、连不上家里（v6）。

**选项**：
- A. v6 补守卫，向 v4 对齐。
- B. 反过来：删掉 v4 守卫，两个族都「封锁时家里也不许连」。

**结论**：**A**。

**理由**：**用户当场裁定（grill 问题 1）**「孩子家里设备 IPv4 IPv6 都要能连，孩子设备上外网要管控」。这是产品意图的直接表述，也说明「家长控制管的是上网，不是家里」。B 会把 v4 从第一版就有的设计推翻，属于更大的行为变更，且与用户意图相反。→ v4 守卫集合因此成为**不可动的基线**（见 ADR-5）。

## ADR-2（数据源）用 `ip -6 route show dev <dev>`，不用 UCI 里的地址字段

**背景**：家里 v6 前缀有三个来源：`network.lan.ip6assign='60'`（不是地址）、`network.globals.ula_prefix='<…>::/48'`（是 **/48 聚合**，比 br-lan 实际用的 /64 宽）、ISP 动态委派的 GUA（UCI 里根本没有）。

**选项**：
- A. 从 UCI 拼：`ula_prefix` + 从 `ip -6 addr show` 读 GUA。
- B. 读内核路由表 `ip -6 route show dev <dev>`，**只取直连（on-link）前缀**。

**结论**：**B**。

**理由**：**A 的三个来源各有一个坑**：`ip6assign` 是长度不是地址；`ula_prefix` 是 /48 而 br-lan 实际是 /64（拿 /48 去放行会**比 v4 放得更宽**，把不属于 br-lan 的 ULA 段也放进来）；GUA 在 UCI 里不存在，只能问内核。**B 一次拿到全部且语义精确**——直连路由就是「这些网段在我这块网卡上，不用经过别的路由器」，正是「家里」的定义（真机实测 br-lan 恰好 3 行：GUA `/64`、ULA `/64`、`fe80::/64`，全是 `pref medium` 的直连条目）。**输出格式与 `pc_lan_nets()` 对齐**（`<prefix>/<len>`，直接就是 CIDR），且 `iptables` 侧无需任何前缀运算（v4 的 `ip/netmask` 点分形式是 **iptables 自己**归一成 CIDR 显示的，脚本里从来没有运算）。

## ADR-3（格式白名单，安全关键）只收形如 `<hex>:<hex>/<len>` 的行首字段

**背景**：`pc_lan_nets6()` 要在 `ip -6 route` 的输出里逐行取「prefix」。真机实测：

```
$ ip -6 route show dev br-lan
<lan-v6-gua>/64 proto static metric 1024 pref medium
<lan-v6-ula>/64 proto static metric 1024 pref medium
fe80::/64       proto kernel metric 256  pref medium

$ ip -6 route show dev lo
unreachable <…b200>::/64 proto static metric 2147483647 pref medium
unreachable <…b201>::/64 proto static metric 2147483647 pref medium
unreachable <…ula>::/48  proto static metric 2147483647 pref medium
```

**行首字段并不总是网段**：`lo` 那张表的三行行首是 **`unreachable`**；全表里还有 `default from <…> via <…> dev eth1 …`。

**选项**：
- A. 取行首字段；` via ` 行剔除；含 `:` 才收。
- B. **白名单**：行首字段必须匹配 `^[0-9a-fA-F:]+/[0-9]+$`，否则整行丢弃。

**结论**：**B**。

**理由**：**A 有两个真实失效**。① `unreachable` 会被当成网段（含 `:` 吗？不含——但这是「顺便挡住」，不是有意为之；换个 kernel 输出顺序就翻车）。② 真正的灾难在**默认路由**：`default from … via … dev eth1` 靠 ` via ` 侥幸被剔掉，**但只要有一条不带 ` via ` 的默认路由（`default dev <dev>`），A 就会把它当成「家里」→ 对整个互联网 RETURN → 封锁彻底失效**（受管设备在封锁窗口照上小红书）。这是**静默、只在封锁时刻暴露、且方向不安全**的失效模式。B 用一条正则同时拒掉 `unreachable` / `default` / `throw` / `blackhole` / 任何非前缀行首，**不需要逐个枚举**——枚举法总会有遗漏，白名单不会。**负向证据**：本条的变异用例（把白名单改成取行首字段 + 注入 `default dev br-lan`）必须让测试 FAIL（见 testplan W 组）。

**⚠ 补充（2026-10-09 阶段 5 SF-1）**：白名单**不是万能的** —— `::/0`（全零前缀的**数字形式**）能通过 `^([0-9A-Fa-f]*:)+[0-9A-Fa-f:]*/[0-9]+$`，进链后即 `-d ::/0 -j RETURN` = 放行一切 → 封锁静默失效。真机上不成立（busybox `ip` 打印 `default`，2026-10-09 只读核实：`ip -6 route show` 三行默认路由均为 `default from … via …`，无 `::/0` 字面量），但必须补一条**零长前缀排除**（拒绝 `/0`）并配 `::/0` 注入用例与变异（M-F3-04）。

**⚠ 补充之二：` via ` 排除不是冗余**。行首可以是**合法前缀**却被 ` via ` 修饰（`<prefix> via fe80::1 dev br-lan` = 下游路由器经 br-lan 通告的转发路由），白名单只看行首字段的**格式**、不看后面的字段，**拦不住**这一行 → 必须额外做**行级** ` via ` 检查。两者是不同层次、都必需。

## ADR-4（不新增规则类别）只用既有 `-j RETURN`，不引 addrtype / ipset / nft

**背景**：更「干净」的做法本可以用 `-m addrtype --dst-type LOCAL` 一条顶掉所有网段枚举。

**选项**：A. 引入 `addrtype`/`ipset`/`nft set`。B. 沿用 `-d <prefix> -j RETURN`，与 v4 完全同构。

**结论**：**B**。

**理由**：**用户硬约束**「不要擅自添加路由表之类的东西」；且真机 **没有 addrtype 模块**（A 直接不可用）。同构带来的额外好处：守卫的生成/幂等/指纹逻辑与 v4 共用同一条路径，评审面小。

---

## ADR-5（v4 基线冻结）不碰 v4 语义，`block_skip_devless()` 仍只吃 lan4

**结论**：`pc_lan_nets()` 一字不改；v4 守卫集合、v4 规则集**逐字节冻结**为验收基线（A2 / D10 ①）。

**理由**：v4 是线上正在生效的资产（iPad 在那张链上），冻结它才能让「本次改动只影响 v6」这件事**可被 md5 证明**，而不是靠口头保证。

## ADR-6（`::1/128` 不特殊处理）不做 v4 `127.0.0.0/8` 的机械移植

**背景**：v4 恰好有 `127.0.0.0/8` 守卫（来自 `loopback` 节）。

**结论**：**不手工加 `::1/128`**。`pc_lan_nets6()` 对 `loopback`（device=`lo`）节的输出是**空**（其路由行首全是 `unreachable`，被 ADR-3 白名单拒掉），这是**正确结果**。

**理由**：发往 `::1` 的报文永远不出主机栈、**不会经过 PREROUTING**，这条守卫在 v6 上**没有任何作用**；v4 那条 `127.0.0.0/8` 同样是「历史遗留、无害但无用」。为对齐而机械添加只会增加评审面与一条无意义规则。**同理**，`fe80::/64` 虽然对转发路径作用有限（link-local 不出网段），但它是**真·直连前缀**，按 ADR-2 如实收录，不做特殊判断 —— **规则统一由数据源决定，不由人工挑拣**。

## ADR-7（验收口径）三条精确判据（修正原 D10）

**背景**：spec 初稿写「iPad 完整性检查不再适用、需放宽」。**这是错的**。

**结论**：经查证，既有检查是**按 iPad MAC 过滤** mangle 规则后取 md5，而新增守卫 `-d <prefix> -j RETURN` **不含 `-m mac`**，不会进入该名单 → 原检查依然成立。改用**三条判据**（写入 D10 / A2 / A9）：

1. v4 侧与 iPad-v4 指纹**逐字节不变**（72 / 53 / `4de4df07…`）；
2. v6 侧 **iPad-v6 指纹逐字节不变**（`3f2ab84d…`）；
3. v6 侧增量**恰好 3 条守卫**（54→57 / 39→42），多一条少一条或夹带其它均 FAIL。

**理由**：判据 3 比原来的「不变」**信息量更大**——它不能证明「没动」，还能指出「**动的正好是预期的那些**」。放宽验收标准会让「改动是否超范围」失去机器可检的证据，是评审的倒退；而实际并不需要放宽。（原判「不适用」源于把「整链 md5」与「按 MAC 过滤后的 md5」混为一谈。）

## ADR-8（版本与打包）1.8.2 / 20261009 / tag `v1.8.2`，用既有可复现脚本

**理由**：F5 轮已把 `test/build_ipk.sh` 做成**可复现**（gzip `-n` + 冻结 mtime；两次构建 md5 相同）。本轮沿用同一脚本，不引入新的打包路径 —— 交付物「怎么造出来的」也必须可复现，否则真机验证的是孤例。

## ADR-9（不改既有 DNS 行为）O3 明确不做

**背景**：v4 的 `-d <lan-v4-cidr> -j RETURN` 会放行「发往路由器的 DNS 查询」，导致 `-m udp --dport 53 -m string` 那条 DNS 串规则拦不到本机 DNS。v6 加守卫后会出现**同样**的行为。

**结论**：**保持一致，本轮不改**。

**理由**：这是 **v4 从第一版就有的既有行为**，与 F3（v6 缺守卫）是两件事。顺手改它属于**未经需求的行为变更**，会污染本次「族同构」的判定边界（评审无法回答「v6 的 DNS 到底该不该拦」）。要改必须单独立项（记入 Out of scope O3）。另外，实际拦截主力是**解析后 IP 段 DROP** 与 **TLS SNI 串匹配**（ClientHello 明文含域名），不依赖 DNS 串规则。
