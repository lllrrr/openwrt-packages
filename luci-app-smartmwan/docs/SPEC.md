# 任务书：高版本 OpenWrt 专用 Rust 多 WAN 智能负载均衡插件（原始需求）

> 本文件是仓库所有者下达的**原始任务书全文**（未删改），是全部实现与验收的最终依据。
> 与本文件的任何偏离都必须在 `docs/REQUIREMENTS.md`（验收矩阵）或 `docs/PROGRESS.md`
> （差距清单）中如实记录，不得静默降级。

## 一、项目目标

开发一套完整、可安装、可构建、可测试的 OpenWrt / ImmortalWrt 高版本多 WAN 管理插件。

项目暂定名称：`luci-app-smartmwan`

核心技术栈：

- 后端：Rust
- 前端：LuCI 原生 JavaScript + uCode
- UI 布局：CSS Grid + Flexbox
- 数据平面：Linux 策略路由 + firewall4 + nftables
- 系统配置：UCI
- RPC：ubus / rpcd
- 软件包：适配目标版本的 APK 构建与安装流程

项目必须兼容高版本 OpenWrt / ImmortalWrt，优先面向 OpenWrt 25.12 及更新版本，以及对应的 ImmortalWrt 高版本分支。

正式实现前，必须检查目标固件的实际版本、架构、内核、LuCI API、uCode 运行环境、rpcd ACL、firewall4 规则接口和包管理方式。不得假定不同固件分支的接口、依赖及构建流程完全相同。

## 二、强制技术约束

### 2.1 完全禁止 Lua

本项目不允许使用 Lua 实现任何功能。

禁止新增、保留或调用以下形式的项目代码：

- `*.lua`
- Lua 版 LuCI Controller、Model、View
- Lua 版 RPC 服务或后台业务逻辑
- 依赖 Lua 执行业务逻辑的脚本
- 为兼容旧版而保留的 Lua 实现
- 将新功能包装成 Lua 再调用 Rust 的实现

LuCI 前端使用目标版本支持的原生 JavaScript、uCode 及其标准接口。系统服务使用 Rust。构建工具链中若存在系统自身提供的 Lua 组件，不得将其误判为本项目业务代码；但不得为插件引入 Lua 运行时依赖。

必须在最终检查中扫描项目源码、安装清单、构建依赖和运行入口，确认没有插件自有 Lua 文件或 Lua 业务依赖。

### 2.2 Rust 后端

使用 Rust 编写独立、长期运行的系统服务。

要求：

- 优先使用稳定版 Rust 和目标固件可用的工具链。
- 采用模块化架构，职责明确，避免单文件堆积。
- 优先使用成熟、维护活跃的依赖；能通过标准库可靠完成的任务，避免引入不必要的第三方依赖。
- 正确处理并发、异步任务、资源释放、超时、错误传播和服务退出。
- 配置文件读取必须具备校验、默认值、版本兼容和错误报告机制。
- 禁止通过拼接用户输入执行 shell 命令。
- 外部命令调用必须使用参数数组，并设置超时、退出码检查和输出长度限制。
- 优先使用可靠的系统 API、netlink 或现有 OpenWrt 接口获取网络状态，避免频繁启动外部进程。
- 不得使用高频全量规则重建的方式实现实时选路。
- 禁止静默吞掉错误；日志必须提供时间、模块、操作、错误原因及必要上下文。
- 不得将敏感信息写入普通日志。

根据目标架构和 Rust 工具链选择可用依赖，确保能在目标 OpenWrt SDK 或受支持的交叉编译环境中重复构建。

## 四、多 WAN 全局工作模式

提供两个可切换的全局工作模式。

### 4.1 负载均衡模式

支持多条 WAN 同时承载业务流量，具备：

- 多 WAN 接口自动发现和手动选择。
- 独立配置线路启用状态、权重、优先级和检测目标。
- 每条线路独立健康检测。
- 不可用线路自动退出分流池。
- 线路恢复后经过恢复确认再重新纳入分流池。
- 普通流量根据所选算法分流。
- 可用线路发生变化时安全更新调度状态。
- 现有连接尽可能保持原出口，避免因策略频繁变化而断线。

### 4.2 主备模式

支持指定主线路和多级备用线路。

要求：

- 可指定主线路及备用线路顺序。
- 主线路健康时，普通业务只使用主线路。
- 主线路故障后，自动选择优先级最高的健康备用线路。
- 当前备用线路故障时，继续选择下一个可用备用线路。
- 主线路恢复后支持自动回切和手动回切。
- 支持回切延迟、连续成功次数、稳定预热时间和防抖。
- 支持强制切换、手动恢复、线路维护和临时禁用。
- 线路角色变化时同步更新策略路由、防火墙标记和相关状态。
- 不允许健康检测短暂抖动导致主备线路频繁切换。

主备模式下，备用线路默认不承担普通业务流量。若启用了游戏低延迟例外，必须通过明确的独立配置允许指定游戏流量使用备用线路。

## 五、负载均衡算法

在 LuCI 页面中提供以下算法。

### 5.1 源 IP（SrcIP）

根据内网源 IP 地址进行稳定哈希分配。

适合希望同一客户端尽量固定使用同一出口的场景。

### 5.2 源 IP + 源端口（SrcIP + SrcPort）

根据内网源 IP 和源端口进行哈希分配。

需要明确该策略对连接稳定性和分流均匀度的影响，不得宣称它能够保证所有连接都均匀分布。

### 5.3 源 IP + 目的 IP（SrcIP + DstIP）

根据源地址和目标地址进行稳定分流。

### 5.4 源 IP + 目的 IP + 目的端口（SrcIP + DstIP + DstPort）

根据指定字段进行哈希分流，适用于多目标、多端口、多连接业务。

若底层实现实际采用完整五元组或其他字段，必须在 UI 和文档中如实描述，不得将不同哈希策略混为一谈。

### 5.5 新建连接数（Least New Connections）

统计每条线路在指定时间窗口内的新建连接数量，优先将新连接分配到负载较低的线路。

要求：

- 定义连接统计窗口和采样频率。
- 排除已失效线路。
- 使用平滑、限幅和最小切换间隔。
- 避免并发新连接同时选中同一条线路。
- 明确统计误差及高连接速率下的性能开销。

### 5.6 实时流量（Least Traffic）

采集各线路实时上下行字节数和速率，结合权重、容量及健康状态选择出口。

要求：

- 通过接口计数器获取流量。
- 使用明确的统计窗口和采样间隔。
- 支持带宽上限和线路权重。
- 不能只看瞬时流量；应使用平滑后的负载指标。
- 不得在每次采样时重建整套 nftables 规则。
- 提供动态调度状态及统计值。

### 5.7 加权哈希 / 加权 ECMP

使用线路权重影响多路径流量分布。

要求：

- 支持不同线路带宽比例，例如 20M:10M:5M 对应 4:2:1。
- 权重范围、默认值和归一化规则必须明确。
- 验证目标内核、路由工具及 netifd 实际支持的多路径能力。
- 不得将权重比例描述为精确的实际带宽占比。
- 单个连接不能因普通 ECMP 自动获得多条 WAN 的带宽叠加。

对无法由当前内核或固件接口原生支持的算法，必须实现经过验证的调度逻辑或明确报告限制，不得在 UI 中提供无法实际生效的选项。

## 六、游戏白名单与低延迟选路

实现独立游戏选路模块。

### 6.1 匹配方式

支持：

- 预置游戏规则。
- 自定义 IPv4/IPv6 目标网段。
- TCP/UDP 协议及端口范围。
- 按 LAN 客户端 IP/MAC 选择设备。
- 可选域名规则和动态 nftables 地址集合。
- 规则启用、禁用、优先级和冲突检查。

预置游戏数据必须可维护、可更新、可手动编辑。不得虚构游戏服务器 IP 或端口。域名匹配必须明确 DNS 缓存、CDN、DoH、硬编码 IP、IPv6 和地址过期等限制。

### 6.2 线路质量指标

每条线路至少维护：

- 链路可用状态。
- 网关可达状态。
- 端到端探测状态。
- RTT 平滑值。
- RTT 抖动。
- 丢包率。
- 连续成功与失败次数。
- 最近一次检测时间。
- 当前调度状态和切换原因。

应支持多个探测目标，避免单一目标屏蔽 ICMP 或发生故障时误判整个 WAN。

### 6.3 自动选路策略

游戏流量优先选择可用线路中延迟低、抖动小、丢包低的线路。

建议使用可配置的综合评分，示例：

```text
score = 100
        - rtt_weight * normalized_rtt
        - jitter_weight * normalized_jitter
        - loss_weight * normalized_loss
        - instability_penalty
```

要求：

- 对输入指标进行校验、归一化和限幅。
- 评分参数可配置。
- 使用滑动窗口和平滑处理。
- 采用滞回和最小稳定时间，避免频繁换路。
- 评分相近时优先保留当前出口。
- 所有线路质量不佳但仍可用时，选择评分最高的可用线路。
- 所有线路均不可用时，进入明确的故障状态并记录原因。

游戏选路必须遵守全局工作模式：

- **负载均衡模式：** 可在所有健康线路中择优。
- **严格主备模式：** 游戏也遵守主备顺序。
- **主备 + 游戏例外模式：** 允许指定游戏流量跨线路择优，但不得改变普通业务的主备策略。

必须在 UI 中清楚展示当前策略，避免用户误以为严格主备模式下的备用线路会承担游戏流量。

## 七、健康检测和故障切换

实现可靠的线路状态机，至少包含：

```text
UNKNOWN
  ↓
HEALTHY
  ↓
DEGRADED
  ↓
FAILED
  ↓
RECOVERING
  ↓
HEALTHY
```

具体状态转移条件应可配置，并通过单元测试验证。

建议初始参数：

- 探测周期：1000ms。
- 单次探测超时：800ms。
- 连续失败 3 次后判定故障。
- 连续成功 5 次后进入恢复确认。
- 恢复预热时间：5 秒。
- 切换采用滞回和最小稳定时间。

以上参数只是默认建议，应允许按线路类型调整。不得将其视为所有 5G 模组、运营商和网络环境的固定最优值。

探测任务必须有并发上限、超时、取消机制和资源限制。5G 模组切换、接口重拨、网关变化和 IPv6 状态变化均应触发必要的重新评估。

## 八、Linux 策略路由与 nftables

使用目标固件实际支持的 firewall4、nftables、策略路由和 netifd 能力。

必须实现：

- 独立路由表与 fwmark 管理。
- 规则优先级及标记掩码冲突检查。
- 每条 WAN 的网关、源地址和路由可用性校验。
- 连接标记与包标记的正确协调。
- 已建立连接的出口保持策略。
- 新连接分类与分流。
- NAT 和回程路由的一致性检查。
- IPv4/IPv6 分开管理和验证。
- 与系统现有防火墙规则安全共存。
- 规则变更前校验、应用后验证、失败回滚。
- 服务停止和卸载时只清理本插件拥有的规则。
- 不得覆盖或删除用户手工维护的防火墙规则。

必须检查目标版本的 `/etc/nftables.d/`、firewall4 include 机制及规则优先级。不得假定所有版本对自定义链、include 文件或优先级的处理完全相同。

不要通过清空整张 nftables 表来更新插件规则。所有规则必须拥有可识别的命名空间和所有权边界。

## 九、Rust 后端 RPC 与配置管理

设计稳定的 RPC 接口，供 LuCI 页面调用。

至少支持：

- `status`：获取全局状态和当前模式。
- `interfaces`：获取 WAN 接口列表及线路信息。
- `get_config`：读取配置。
- `validate_config`：校验配置但不应用。
- `apply_config`：事务式应用配置。
- `switch_mode`：切换负载均衡或主备模式。
- `set_primary`：设置主线路。
- `set_backup_order`：设置备用线路顺序。
- `set_algorithm`：设置负载均衡算法。
- `get_quality`：获取线路质量指标。
- `get_traffic`：获取实时流量。
- `get_connections`：获取连接统计。
- `get_game_rules`：读取游戏规则。
- `update_game_rules`：更新游戏规则。
- `force_failover`：执行经校验的手动切换。
- `failback`：执行经校验的回切。
- `get_events`：获取最近事件与错误。
- `diagnostics`：生成只读诊断结果。

RPC 返回统一结构，包含成功状态、数据、错误码、可读错误信息和必要的时间戳。

使用目标版本支持的 rpcd/ubus 机制注册服务和 ACL。不得假定 RPC 的所有权、参数格式或权限接口无需验证。

对修改系统路由、防火墙和服务状态的接口实施严格权限检查、输入校验、并发互斥和审计日志。只读接口不得附带修改系统状态的副作用。

## 十、LuCI 前端与 UI 设计

使用目标版本支持的原生 LuCI JavaScript/uCode，不使用 Vue、React、Angular 等大型前端框架，除非目标 SDK 已有明确且合理的基础设施需求。

### 10.1 页面结构

采用多 Tab 管理界面：

1. **运行总览**
   - 当前工作模式。
   - 当前主线路与备用线路。
   - 各 WAN 在线状态。
   - RTT、抖动、丢包率。
   - 上下行实时速率。
   - 当前选路策略。
   - 最近切换事件。

2. **线路管理**
   - WAN 自动发现。
   - 启用与禁用线路。
   - 接口、网关、地址和路由状态。
   - 权重、优先级和带宽上限。
   - 健康检测目标和状态。
   - 手动检测与诊断。

3. **负载均衡**
   - 全局算法选择。
   - 权重配置。
   - 连接数或流量动态调度参数。
   - 哈希与会话保持设置。
   - 算法实际支持状态和能力说明。

4. **主备切换**
   - 主线路选择。
   - 多级备用线路排序。
   - 自动回切或手动回切。
   - 故障检测阈值。
   - 恢复预热和切换防抖。
   - 强制切换与回切操作。

5. **游戏低延迟**
   - 游戏预设。
   - 自定义 IP、协议、端口规则。
   - 客户端匹配规则。
   - 动态域名集合设置。
   - 评分权重。
   - 严格主备或游戏跨线路择优。
   - 当前游戏规则命中情况与选路原因。

6. **连接与流量**
   - 各 WAN 实时流量。
   - 连接数量。
   - 各线路流量分布。
   - 规则命中统计。
   - 当前会话出口统计。

7. **系统设置**
   - 检测周期和超时。
   - 日志等级与保留策略。
   - 服务启停。
   - 配置导入、导出和校验。
   - 诊断信息和版本信息。

### 10.2 CSS Grid + Flexbox

所有页面布局优先使用 CSS Grid 和 Flexbox，确保 PC 与移动端自适应。

要求：

- 总览使用 CSS Grid 构建响应式状态卡片。
- 表单、按钮组、工具栏和状态行使用 Flexbox。
- 宽屏充分利用空间，移动端自动调整列数和排列。
- 使用 `minmax()`、`auto-fit`、`auto-fill` 和合理的断点设计。
- 避免固定宽度导致横向滚动。
- 表格在窄屏下采用可读的滚动容器或卡片布局。
- 统一卡片、输入框、选择器、开关、提示框和确认弹窗样式。
- 清晰展示加载、空数据、无权限、RPC 失败和服务离线状态。
- 支持键盘导航、焦点可见性、语义化标签和适当的颜色对比。
- 使用轻量 SVG 绘制线路拓扑、状态图标和流量趋势。
- 不使用大量无意义动画，不因刷新数据导致页面闪烁。
- 禁止直接修改 LuCI 全局样式造成其他插件显示异常。
- 样式必须作用域化，避免污染其他页面。
- 前端应遵守 LuCI 当前版本的依赖加载和视图生命周期约定。

## 十一、UCI 配置

提供可读、可校验的 `/etc/config/smartmwan`。

配置至少涵盖：

- 全局启用状态。
- 全局工作模式。
- 负载均衡算法。
- WAN 接口及角色。
- 权重、优先级和带宽限制。
- 健康检测配置。
- 主备切换与回切策略。
- 游戏白名单与预设。
- 游戏选路例外。
- 质量评分权重。
- 连接保持和切换防抖。
- 日志与诊断配置。

必须提供配置迁移策略和默认配置。

保存配置与应用配置应分离。用户点击应用前，先进行完整校验并显示变更摘要。应用失败必须保留原有效配置或恢复到已知安全状态。

## 十二、安全性与稳定性

必须重点审查以下风险：

- 用户输入导致命令注入。
- nftables 规则注入。
- UCI 配置损坏或字段类型错误。
- RPC 权限过宽。
- 多个配置事务并发执行。
- 服务重启导致规则重复。
- 线路切换导致连接标记与路由表不一致。
- 旧规则残留或误删用户规则。
- 5G 模组重新拨号后网关变化。
- IPv6 流量意外绕过策略。
- 探测任务过多造成 CPU、内存或网络负载上升。
- 前端重复轮询、RPC 堆积和页面销毁后仍有后台任务。
- 配置错误导致路由器失去管理连接。

应用配置前必须验证新规则。存在断网风险时，应提供安全回滚机制和明确的二次确认。默认禁止未经确认的破坏性操作。

## 十三、构建与安装

提供完整的 OpenWrt / ImmortalWrt 高版本构建方案：

- Makefile。
- Cargo 构建与交叉编译配置。
- 目标架构检测。
- 软件包依赖声明。
- APK 包生成。
- 服务安装与启停。
- LuCI 菜单和 ACL 安装。
- UCI 默认配置安装。
- nftables 规则安装。
- 软件包升级、卸载和回滚处理。
- 构建产物校验。
- 可复现构建说明。

必须以实际目标版本的 SDK、工具链和软件包元数据为准。不得将传统 `opkg` 流程不加验证地用于 OpenWrt 25.12+。若目标 ImmortalWrt 分支使用不同的包管理或构建约定，必须按该分支实际实现调整。

安装包不得自动覆盖用户已有网络配置。首次启用前应检查当前网络环境，并明确提示需要修改的项目。

## 十五、执行方式

请先检查现有仓库、目标固件版本、官方 SDK 和当前 LuCI/uCode 接口，再制定实施计划。

然后按以下顺序执行：

1. 审计现有项目和目标平台兼容性。
2. 确定配置模型、RPC 协议和数据平面设计。
3. 实现 Rust 服务与线路状态机。
4. 实现策略路由、nftables 和安全事务。
5. 实现负载均衡算法与主备切换。
6. 实现游戏白名单及低延迟选路。
7. 实现 LuCI 原生 JavaScript/uCode 页面。
8. 实现 CSS Grid + Flexbox 响应式 UI。
9. 实现软件包构建、安装、升级和卸载。
10. 执行自动化测试、构建和目标设备验证。
11. 修复发现的问题，提交最终变更与测试报告。

每个阶段都必须给出真实完成状态、修改文件、测试命令、测试结果及剩余问题。

优先确保网络安全、数据平面正确和功能完整，再进行 UI 精细化。不得为了快速交付而删除必要的错误处理、权限检查、回滚逻辑或测试。

最终交付完整源码、构建说明、APK 生成方式、安装与卸载说明、配置示例、架构文档和验收报告。
